# Prompt para Agente de Código — DoD i18n + Copies centralizados en `packages/shared` (Web + Mobile)

## Contexto del repo
Monorepo con:
- `./apps` (web y mobile)
- `./packages/shared`

Queremos centralizar *todos* los textos (copies) de ambas apps en `packages/shared`, pero sin acoplar `shared` a ninguna librería de i18n (ni next-intl, i18next, react-intl, expo-localization, etc.). Cada app consumirá esos copies usando SU propia librería/patrón.

---

## Definition of Done (DoD) — Obligatorio
1) **Todos los copies** (web y mobile) viven en `packages/shared`.
   - Incluye: títulos, subtítulos, empty states, labels, CTAs, errores, tooltips, toasts, textos de invitado/solo lectura, pluralizaciones, etc.
2) **Mobile/app** debe leer el copy desde `packages/shared` y resolver el idioma con **su** librería de i18n.
3) `packages/shared` **no puede** importar ni depender de ninguna librería específica de i18n o UI.
   - Solo TypeScript/JS puro, funciones puras y objetos.

---

## Requisitos técnicos (arquitectura)
### A) Estructura en `packages/shared`
Crear un módulo de copies desacoplado, por ejemplo:

packages/shared/src/copy/
index.ts
locales/
en.ts
es.ts
pl.ts (opcional)
types.ts
helpers.ts


#### `types.ts`
- Definir el tipo de diccionario (ej. `CopyDictionary`) y la lista de claves válidas (evitar strings sueltas si es posible).
- Soportar interpolación con variables (ej. `{count}`, `{accountName}`) y pluralización básica.

#### `locales/*.ts`
- Exportar objetos planos por idioma: `{ home: { title: "...", empty: "...", ... }, ... }`
- Sin dependencias externas.

#### `helpers.ts`
- Implementar helpers puros:
  - `getDictionary(locale: string): CopyDictionary` (fallback a `en` o `es`)
  - `t(dict, key, params?)` -> string (interpolación simple)
  - `pluralize(locale, { one, other }, count)` -> string
- Importante: esto NO es una librería i18n completa; es un set mínimo reutilizable sin acoplarse a frameworks.

#### `index.ts`
- Exportar:
  - `getDictionary`
  - `t`
  - `pluralize`
  - Tipos

### B) Consumo en Mobile (obligatorio)
En `apps/mobile`, integrar el diccionario de `shared` con su i18n actual:
- La app detecta locale con su método (ej: i18next/expo-localization/lo que uses).
- Carga el diccionario desde `packages/shared`.
- Mapea el diccionario al mecanismo de traducción de la app:
  - Opción 1: usar el `t(dict, key, params)` de shared directamente en componentes.
  - Opción 2: registrar recursos en la librería de i18n de mobile usando el objeto de shared (preferred si ya tienes i18n montado).

**Regla:** Mobile NO debe duplicar textos; solo “lee” y resuelve idioma.

### C) Consumo en Web (recomendado y coherente con DoD 1)
En `apps/web`, misma idea:
- Web detecta locale con su mecanismo.
- Usa diccionarios de `shared` como fuente única.
- Puede usar `t(...)` de shared o registrar recursos en su i18n de web.

---

## Migración (pasos)
1) Buscar y eliminar copys hardcodeados en web y mobile.
2) Moverlos a `packages/shared/src/copy/locales/{lang}.ts`.
3) Reemplazar en apps el texto por llamadas a traducción basadas en shared:
   - `const dict = getDictionary(locale)`
   - `t(dict, "home.hero.title", { month: "Enero" })`
4) Asegurar interpolaciones y pluralizaciones:
   - “1 participante” vs “2 participantes”
   - “{count} cuentas” etc.
5) Añadir tests unitarios en `packages/shared` para:
   - Interpolación
   - Pluralización
   - Fallback de locale

---

## Criterios de aceptación
- No existe ningún copy en `apps/mobile` ni `apps/web` (salvo keys o wiring mínimo).
- `apps/mobile` resuelve idioma usando su librería, leyendo recursos desde `packages/shared`.
- `packages/shared` no depende de ninguna librería de i18n y no importa nada fuera de TS/JS estándar.
- El build de web y mobile funciona y el idioma cambia sin romper textos.


## guardarraíl
NO instalar nuevas dependencias para i18n; usar lo que ya existe en cada app.
